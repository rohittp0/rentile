# Migrating from 0.12.0 to 0.12.1

`0.12.1` is a fix release. **Line and line-center label text is now laid out on one line, as Mapbox
lays it out.** No public type or signature changes: `checkKotlinAbi` reports no JVM or klib change,
so `0.12.1` is a drop-in replacement for `0.12.0` and needs no recompile. The two label-candidate
keys move. The source tree declares `VERSION_NAME=0.12.1`, which requests the release but does not
prove it was published. Upgrade only after `com.rohittp.rentile:kmp:0.12.1` resolves from
`https://maven.rohittp.com`.

## What changed

In `0.12.0` a Label Candidate whose `placement` is `LINE` or `LINE_CENTER` was laid out like a point
label. Its text wrapped at `text-max-width`, 10 em unless the style said otherwise, so a long road or
river name arrived as two or more rows of glyphs. Mapbox never wraps such text. It reads
`text-max-width` for point placement only and shapes every other placement with an unbounded width.
Mapbox GL JS v3.32.0, `src/symbol/symbol_layout.ts` lines 400-402:

```ts
const isPointPlacement = symbolPlacement === 'point';
const maxWidth = isPointPlacement ?
    layout.get('text-max-width').evaluate(feature, {}, canonical) * ONE_EM :
    Infinity;
```

With that width, `determineAverageLineWidth` (`src/symbol/shaping.ts` line 402,
`Math.max(1, Math.ceil(totalWidth / maxWidth))`) targets a single line that holds the whole text.
MapLibre GL JS has the same rule, at `src/symbol/symbol_layout.ts` lines 156-158 of `main` at
`812e3700` (2026-10-08).

Under both compatibility profiles:

- **A `LINE` or `LINE_CENTER` candidate's `glyphs` are one row**, in reading order, with each word
  separated by its space advance and letter spacing. Its `boundingBox` is that row's extent. Both
  equal what the same text yields as a point label with a `text-max-width` that the text never
  reaches.
- **`text-max-width` is not evaluated for a line placement.** A feature whose `text-max-width`
  evaluated to something unusable used to be skipped, and was counted in `LABEL_FEATURE_SKIPPED`.
  Placed along a line, it now yields its candidate. Placed at a point, it is still skipped.
- **`POINT` candidates are unchanged.** They wrap at `text-max-width` exactly as before.
- **`text-justify` is unchanged.** Mapbox forces centre justification on text along a line
  (`symbol_layout.ts` lines 396-398). On a single row every justification places the glyphs the
  same way, so the style's own value is kept and has no effect.

## Why this is not opt-in

[ADR 0026](../adr/0026-repaired-layers-degrade-and-author-intended-layers-fail.md) sets the bar for a
change of this kind: nothing that worked may stop working. This change clears it without a flag.

- **The wrapped rows were a fidelity bug, not a capability.** No Mapbox or MapLibre style can produce
  wrapped text along a line, so no style author asked for it, and no consumer that reproduces either
  renderer could use it. Travel Animator, the consumer
  [ADR 0035](../adr/0035-the-host-can-own-every-symbol-layer.md) names, joined the rows back together
  on the host by estimating the gaps between words. A flag would have kept a layout that no style can
  ask for.
- **Nothing that succeeded can now fail.** Preparation is unchanged: `text-max-width` is still
  compiled and validated there, with the same diagnostics, and `PreparedStyle.digest` does not move.
  Output Tiles contain no label text, so no pixel and no output key moves. A candidate's text uses the
  same codepoints, so the batch acquires the same Glyph Ranges and packs the same glyph atlas, under
  the same atlas key. No safety limit reads a candidate's row count or box. The only code path
  removed is a failure: evaluating `text-max-width` for a line label.
- **What changes is candidate geometry, and the keys say so.** Both label keys move, so no cache keyed
  on them can serve `0.12.0`'s rows.

## Cache invalidation

| Identity | `0.12.0` | `0.12.1` | Action |
|---|---|---|---|
| Label candidate request key | `label-candidates-3` | `label-candidates-4` | Recompute every lookup key. |
| Label candidate batch content key | `rentile-label-candidates-3` | `rentile-label-candidates-4` | Discard cached candidate batches. |
| Glyph atlas content key | unchanged | unchanged | Keep uploaded glyph textures. |
| Output request and content keys | unchanged | unchanged | Keep Output Tile caches. |
| `PreparedStyle.digest` | unchanged | unchanged | Keep identities derived from it. |
| Raw resources | unchanged | unchanged | Keep the raw cache. |

The markers move for every batch, including one with no line labels, whose candidates are unchanged.
The request key is computed from style and tile identity before anything is fetched, so it cannot
tell whether a tile set holds line labels.

## What you have to do

1. Raise the version. Nothing needs recompiling.
2. Discard label caches keyed by the `0.12.0` markers. A cache keyed on Rentile's own keys misses on
   its own.
3. If your host joins the rows of a line candidate back into one line, delete that code. A line or
   line-center candidate is already one row.

## What did not change

Rentile still does not force a line break at a `\n` in a label's text, under any placement. Mapbox
does, because a newline carries a break penalty of -10000 (`src/symbol/shaping.ts` lines 426-428).
That penalty applies even under the unbounded width above, so a line label whose text contains a
newline is two rows in Mapbox. This difference predates `0.12.1`, and this release leaves it as it
was.
