# Migrating from 0.8.x to 0.9.0

`0.9.0` is a deliberate minor while Rentile is prerelease. The source tree declares
`VERSION_NAME=0.9.0`; that declaration requests the release but does not prove it has been
published. Upgrade only after `com.rohittp.rentile:kmp:0.9.0` resolves from
`https://maven.rohittp.com` and the release workflow has passed.

`RenderOptions.outputSizePx` accepts 1024 and 2048 in addition to 256 and 512, and the size is now
a pixel ratio throughout the draw path rather than only in the geometry. No public signature
changes; two things do change behaviour. See
[ADR 0030](../adr/0030-scale-the-output-tile-by-its-pixel-ratio.md).

## Why it exists

Style pixel values are resolution-independent to a vector renderer, so device density costs it
nothing in tile count. Rentile rasterises, so density is paid in tiles. A consumer on a 3x-density
screen renders its camera at `zoom + log2(3)` and, selecting basemap zoom by
`log2(512 / tileSize)`, ends up fetching two levels deeper than a vector renderer would for the
same view — around nine times the tiles, measured at 930 against 104 for one route. At
`tileSize = 2048` that shift becomes `-2`, one tile replaces sixteen, and the device pixels per
unit of ground are unchanged, because `2048 / 512` is exactly the ratio those two zoom levels cost.

## Behaviour changes

### `outputSizePx = 256` renders half-weight ink

This is the one that can surprise you. 256 always meant "the same map at half the pixels", and its
geometry did: a feature landed at the same fraction of the tile at 256 as at 512. Its *ink* did
not. `line-width`, `line-gap-width`, `line-offset`, `line-blur`, `line-translate`,
`fill-translate`, the `fill-outline-color` hairline, `icon-size`, `icon-offset`, `icon-padding`,
`icon-halo-width`, `icon-halo-blur`, sprite pattern periods, collision-box extents and the
`symbol-avoid-edges` bound were all applied as raw output pixels, so a `line-width` evaluating to
14 painted 14 rows into a tile with half the ground resolution. From `0.9.0` it paints 7, which is
what the halved pixel ratio always implied.

If you render at 256 and your output looked right, it was right for a compensating reason. Either
move to 512 — the reference size, byte-identical across this release — or expect thinner strokes,
smaller icons and tighter pattern periods, and re-check any threshold tuned against the old
weights.

512 is unchanged, byte for byte: at the reference size the pixel ratio is one and the transform is
the identity.

### Both output-key markers advance

Because identical style, tile, options and resources can now yield different pixels at 256, the
renderer-semantics markers move: the request key to `rentile-output-request-3` and the content key
to `rentile-output-4`. Every `outputRequestKey` and `RenderedTile.contentKey` therefore changes
value, and a caller-owned output cache keyed on either will miss once and refill. That is the
intended effect — it is what stops a cache serving the previous renderer's tiles. Nothing needs
purging by hand.

Label keys do not move. Label acquisition takes no `RenderOptions` and is untouched by this
release.

## Two unit mismatches fixed on the way

Both followed from the same ambiguity and are worth knowing about if you depended on the old
numbers:

- **`symbol-spacing`** is in style pixels but was compared against arc length in output pixels, so
  a line's repeated-icon count changed with the output size. It no longer does.
- **A collision box's extent** was in style pixels while its centre and the `symbol-avoid-edges`
  bound were in output pixels. All three are in style pixels now, so placement and collision
  outcomes are identical at every size.

## What you must do for labels at 1024 and 2048

Nothing changes in the label API, and that is the point: a `LabelCandidate` is not tied to a
`RenderOptions`, so the same candidates serve a tile drawn at any size. Its pixel-valued scalars —
`padding`, `haloWidth`, `haloBlur`, `translateX`, `translateY`, and the paired icon's `width`,
`height`, `offsetX`, `offsetY`, `padding`, `textFitPadding` — are **style pixels at ratio one**, and
`LabelGlyphQuad.scale` is `text-size / 24` in those same units.

So when you composite labels over a tile rendered at 1024 or 2048, apply `outputSizePx / 512` to
that geometry yourself, exactly as you already apply your device pixel ratio. Nothing in
`LabelCandidateBatch` reports an output size, deliberately: folding one in would put it into the
label request and content keys, which are correct today precisely because a candidate does not
depend on it.

## Limits

Two existing ceilings now cover the output surface as well as source imagery, because the surface
Rentile allocates for itself had no bound while the largest was 1 MiB and is 16 MiB at 2048:

| Limit | Default | Checked against |
|---|---|---|
| `maxRasterDimensionPx` | 8192 | `outputSizePx` |
| `min(maxDecodedRasterBytes, maxResidentDecodedBytes)` | 256 MiB, 128 MiB | `outputSizePx * outputSizePx * 4` |

Neither default was raised: 2048 px and 16 MiB clear both comfortably. The check exists so a host
that has tightened them for a small device gets a `SafetyLimitException` at
`PipelineStage.RASTERIZATION` instead of a Skia allocation failure, and so a future size that
outgrew them would fail a test rather than a device. A refused allocation is also wrapped now —
Skia reports one as a bare `require` failure, which previously crossed the public API untyped and
missed `catch (e: RentileException)`.

## Cost, before you choose 2048

Measured on a host JVM against a 240-line, 2-polygon fixture, best of seven, one tile:

| `outputSizePx` | `render` (draw + PNG) | `renderRaw` | PNG bytes | Surface |
|---|---|---|---|---|
| 256 | 17 ms | 4 ms | 10 KB | 0.25 MiB |
| 512 | 27 ms | 7 ms | 18 KB | 1 MiB |
| 1024 | 57 ms | 14 ms | 39 KB | 4 MiB |
| 2048 | 160 ms | 28 ms | 93 KB | 16 MiB |

Per tile, 2048 costs about 6x what 512 does for 16x the pixels — sub-linear, because the fixed
per-feature work is paid once. Per unit of *ground*, one 2048 tile replaces sixteen 512 tiles, so
the same view costs 160 ms rather than 16 x 27 ms, and 93 KB of PNG rather than 16 x 18 KB. Both
directions favour the large tile.

Two caveats:

- **Latency is per tile, not per view.** A first tile at 2048 takes six times as long to appear as
  one at 512. For a batched or offline consumer that is a straight win; for a latency-sensitive
  interactive one, 1024 is the gentler step.
- **`render` and `renderRaw` retain every tile in the batch at once.** `maxConcurrentMetatileWorkers`
  bounds concurrent *drawing*, not retention, so a 30-tile `renderRaw` batch at 2048 holds about
  480 MB of `rgbaBytes`. Request large tiles in small batches.

## Raster styles gain less

A provider's raster `tileSize` is capped at 512 by the Style Specification set Rentile accepts, so
at 1024 and 2048 the exact source/output pixel-size match that raster pass-through requires can
never hold. Every raster layer takes the composite-and-re-encode path, and a raster basemap is
bilinearly magnified rather than sharpened: it cannot exceed its source. Vector styles get the
full benefit of the large sizes; raster styles get only the reduced request count.
