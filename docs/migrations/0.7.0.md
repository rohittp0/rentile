# Migrating from 0.6.x to 0.7.0

`0.7.0` is a deliberate breaking minor while Rentile is prerelease. The source tree declares
`VERSION_NAME=0.7.0`; that declaration requests the release but does not prove it has been
published. Upgrade only after `com.rohittp.rentile:kmp:0.7.0` resolves from
`https://maven.rohittp.com` and the release workflow has passed.

The release exposes the decoded pixels of an elevation Source Tile. Only terrain acquisition
changes; label preparation, Output Tile rendering, style compilation, caching and the failure
contract are untouched.

## Why it exists

`acquireTerrainTiles` returned `ValidatedDemTile.bytes`, the exact encoded image, and nothing else.
A consumer that wanted elevation therefore needed its own decoder for whichever container the
provider chose. Measured against a real 34-style corpus, five of the six styles declaring a
top-level `terrain` block serve **WebP** DEM tiles and one serves PNG, so a consumer with only a PNG
decoder reaches one terrain style in six.

Rentile already decoded those exact bytes to validate them and discarded the result. `0.7.0` keeps
what that decode produced instead of throwing it away. No second decode is added.

## Public API break ledger

### `ValidatedDemTile`

One field is **appended**, which changes the primary constructor, `copy`, and destructuring.
Recompile every consumer; `0.6.x` binaries are not ABI-compatible with this class.

| `0.6.x` | `0.7.0` | Consumer action |
|---|---|---|
| six constructor parameters ending in `contentDigest: String` | a seventh, `texels: DemTexels` | Recompile. Positional construction of the first six parameters is unchanged, so nothing silently changes meaning. |
| — | `component7()` | Destructuring that bound six components still compiles and still binds the same six. |
| `bytes` | `bytes`, unchanged | Keep hashing `bytes` for cache identity. `texels` is an addition, never a replacement. |

`equals`, `hashCode` and `toString` also change, and this is a **behaviour** change rather than a
signature one. `ValidatedDemTile` was a data class holding a `ByteArray`, so its generated `equals`
compared `bytes` by **reference**: two instances describing the same tile with equal bytes were
unequal. It now compares `bytes` by content, matching `RenderedTile` and `LabelGlyphAtlas`, which
already did. `toString` reports `byteCount` instead of the array's identity hash. A consumer that
depended on reference equality here was depending on a defect.

### `DemTexels`, new

```kotlin
public data class DemTexels(
    public val width: Int,
    public val height: Int,
    public val rgba: ByteArray,
)
```

It compares by content and summarises rather than dumps in `toString`. Its `init` rejects any buffer
that is not exactly `width * height * 4` bytes, and any non-positive dimension.

## What the pixels are, exactly

These guarantees are the whole value of the field, and each is asserted by a test that fails when it
is broken.

- **Canonical RGBA8.** Four bytes per texel in red, green, blue, alpha order — a fixed order, not
  the platform's. Skia's N32 is BGRA on some of Rentile's targets and RGBA on others, so an
  N32-shaped buffer would decode one DEM to different elevations on different targets.
- **Rows top-down, tightly packed.** `rgba[(y * width + x) * 4]` is the red channel of column `x`,
  row `y`, counting `y` from the tile's top — its north edge under XYZ. Row stride is exactly
  `width * 4`; there is no padding. A consumer that uploads these rows bottom-up gets a mirrored
  planet rather than an error.
- **Never premultiplied.** A DEM packs elevation across red, green and blue, so scaling those
  channels by a non-opaque alpha corrupts the elevation silently instead of merely darkening a
  picture. Whatever alpha the encoded image carried is preserved rather than assumed opaque.
- **No colour conversion.** The decode names no destination colour space, so the channel values are
  the ones the image encoded even when it declares a profile.
- **Still encoded in `bytes`.** `texels` is decoded output; `bytes` is the resource. Hash `bytes`.

Elevation itself is unchanged and still the consumer's arithmetic: apply the tile's own
`encoding` (`TerrainDemEncoding.MAPBOX` or `TERRARIUM`) to the red, green and blue channels.
`texels` carries packed channel values, not metres.

## Behaviour changes beyond the signature

- **A corrupt DEM now fails at acquisition.** `Image.makeFromEncoded` is lazy, so validating a
  raster previously parsed the header and constructed a codec without necessarily decoding pixels.
  Terrain acquisition now decodes fully, so a DEM whose pixel data is truncated or corrupt raises
  `ResourceDecodeException` from `acquireTerrainTiles` instead of surfacing later. Dimension and
  memory limits are still enforced from the header, before anything is allocated.
- **Nothing else retains pixels.** Only terrain acquisition asks for them. Hillshade rendering,
  raster sources, substitution and the Output Tile path are byte-for-byte unchanged and hold no
  decoded copy.
- **`maxDecodedRasterBytes` and `maxResidentDecodedBytes` are unchanged**, and still bound a single
  decode. A caller that acquires many terrain tiles at once now holds `width * height * 4` bytes
  per returned tile until it drops them; that is the caller's working set, not a Rentile cache.

## Cache invalidation

None. `contentDigest`, request keys, content keys and Output Tile pixels are unaffected, so no
caller-owned cache entry needs discarding. This is purely an addition to what one acquisition
returns.

## Consumer migration sequence

1. Recompile against `0.7.0`. Only code that constructs or fully destructures `ValidatedDemTile`
   needs editing.
2. Delete any DEM image decoder written to work around the previous gap, and read `texels` instead.
3. Keep hashing `bytes` wherever tile identity is derived from it.
4. If any code relied on `ValidatedDemTile` reference equality, key on `contentDigest` instead.
