# Migrating from 0.11.x to 0.11.2

`0.11.2` is a performance release. It changes no public type, no signature, no key and no pixel, so
this is a version bump and nothing else. The source tree declares `VERSION_NAME=0.11.2`; that
declaration requests the release but does not prove it has been published. Upgrade only after
`com.rohittp.rentile:kmp:0.11.2` resolves from `https://maven.rohittp.com`.

A sprite atlas is now decoded once for a whole prepared batch instead of once for every tile that
batch draws. See
[ADR 0033](../adr/0033-one-decoded-sprite-atlas-serves-a-whole-prepared-batch.md).

## What changed

Nothing you can call. `checkKotlinAbi` reports no change to the JVM or klib ABI, so `0.11.2` is a
drop-in replacement for `0.11.1`: no recompile is required, and an implementer of
`BasemapRasterizer` overrides nothing new.

What changed is inside `render` and `renderRaw`. Every composited tile used to build its own
`SpriteRenderContext`, and that constructor called `Image.makeFromEncoded` on the style's sprite
sheet. `Image.makeFromEncoded` is lazy — it costs microseconds and defers the decode to the first
draw that samples the image, then memoises it against that image — so a fresh image per tile meant a
fresh decode per tile, invisibly. Measured on macOS arm64 with Skiko 0.148.2, rendering 52 tiles with
four sprite extractions each: **265 ms of repeat decoding for a 2048 px sheet, against 10 ms when one
image serves the batch** (48 ms against 1.4 ms for a 1024 px sheet).

## What you have to do

**Discard nothing.** Output request keys, content keys and renderer-semantics markers are all
unchanged, because the pixels are unchanged: the same encoded sheet, the same Skia decode, the same
extraction into the same per-tile surface. Cached raw resources and cached rendered output carry over.

**Nothing about the shape of your calls changes**, but two shapes now differ in cost, both in your
favour:

- Rendering many tiles from **one prepared batch** decodes the sheet once, however many `render` or
  `renderRaw` calls you split those tiles across. A consumer that renders a prepared batch tile by
  tile so it can mark some of them `RenderPriority.URGENT` gets the full saving.
- **Each prepared batch decodes its own.** Two batches of one style decode twice. That is deliberate:
  a `PreparedBatch` is what closes, so it is what can release the decoded pixels. Preparing one batch
  per tile is now the expensive shape, where before every shape was.

**A batch holds decoded sprite pixels until you close it** — roughly 16 MiB for a 2048 px sheet,
nothing at all for a style with no sprite. Closing prepared batches promptly, as
`instructions.md` already shows, is what keeps that to one at a time.

## Raise `maxRequestsPerHost` on an OkHttp-backed transport

This is not a change in `0.11.2`; it is a mismatch Rentile cannot fix from inside the library, and
it costs a consumer real concurrency today.

Rentile's default `ExecutionPolicy` admits 8 concurrent exchanges with 6 per origin. A basemap style
serves nearly everything from one origin, so `maxConcurrentExchangesPerOrigin` is the number that
governs a real session. A `ResourceTransport` backed by Ktor's OkHttp engine dispatches through
OkHttp's `Dispatcher`, whose default `maxRequestsPerHost` is **5** (`maxRequests` defaults to 64 and
is not the binding limit here). Rentile's gate hands the transport a sixth request and OkHttp queues
it, so the sixth permit does nothing and the origin runs one connection short of the policy.

The Ktor engine is what makes this bite: `Dispatcher` bounds *asynchronous* calls, and Ktor's OkHttp
engine issues every exchange through `Call.enqueue`. A transport that calls `Call.execute` on its own
thread is not capped this way and needs no change.

Rentile cannot raise it. ADR 0004 makes the transport host-provided precisely so that no HTTP client
is on Rentile's classpath: it never constructs the `OkHttpClient` or its `Dispatcher`, is handed only
a `ResourceTransport` function, and has no OkHttp types to reach for. The fix belongs to whoever
builds the client:

```kotlin
val client = OkHttpClient.Builder()
    .dispatcher(Dispatcher().apply { maxRequestsPerHost = 6 })
    .build()
```

Match it to whatever `maxConcurrentExchangesPerOrigin` you configure rather than to the literal 6, and
leave `maxRequests` alone. A consumer sharing one `OkHttpClient` with the rest of its app should weigh
that against its other traffic to the same host; the point is that the number be chosen, not
inherited.

## Release completeness

**`0.11.2` is whole.** All eight coordinates are published and signed — `kmp`, `kmp-android`,
`kmp-jvm`, `kmp-iosarm64`, `kmp-iossimulatorarm64`, `kmp-macosarm64`, `kmp-linuxx64` and
`kmp-linuxarm64` — the root metadata's `<release>` is `0.11.2`, and the release workflow's "Verify
public artifacts" and "Resolve from the public repository without credentials" steps both ran and
passed, which they never did for `0.11.0` or `0.11.1`. Checked again afterwards from outside CI, by
requesting each coordinate's POM and each target's `.klib`/`.aar`/`.jar` and signature from
`https://maven.rohittp.com`.

`0.11.0` and `0.11.1` are still published without a `kmp-macosarm64` coordinate while their root
modules advertise the macOS variants, so a `macosArm64` consumer of either still resolves a 404. A
released coordinate is immutable, so that does not change; `0.11.2` is the version to move to. See
the [0.11.1 migration ledger](0.11.1.md).

The stale `kmp-linuxx64/maven-metadata.xml.md5` that ledger recorded — the object whose write raised
the R2 `500` — **is repaired.** This release rewrote that document and its checksums on its way past,
and the published `md5` now matches the document. Step 1 of that ledger's repair is done and should
not be repeated.
