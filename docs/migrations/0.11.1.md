# Migrating from 0.10.x to 0.11.1

`0.11.1` is a deliberate minor's content on the next patch coordinate, while Rentile is prerelease.
The source tree declares `VERSION_NAME=0.11.1`; that declaration requests the release but does not
prove it has been published. Upgrade only after `com.rohittp.rentile:kmp:0.11.1` resolves from
`https://maven.rohittp.com` and the release workflow has passed.

`0.11.1` carries exactly the change described below and nothing else. Two things about the release
itself, which are not about the change and do not affect what it does:

**`0.11.1` is published for `android`, `iosArm64`, `iosSimulatorArm64`, `jvm`, `linuxX64` and
`linuxArm64`, and *not* for `macosArm64`.** Its upload hit an R2 `500` in
`publishLinuxX64PublicationToR2Repository`, writing `kmp-linuxx64/maven-metadata.xml.md5`, and Gradle
abandoned the publications that had not run yet. The root `kmp-0.11.1.module` still advertises
`macosArm64ApiElements-published`, `macosArm64SourcesElements-published` and
`macosArm64MetadataElements-published` as `available-at: kmp-macosarm64:0.11.1`, so **a consumer with
a `macosArm64` target resolves a variant that 404s**, with nothing to say the release was partial.
Every other target resolves and is signed, and the workflow's own "Verify public artifacts" and
"Resolve from the public repository without credentials" steps never ran.

The repair, for someone with R2 credentials, is two steps and neither is a rebuild of a released
artifact:

1. ~~Re-upload `com/rohittp/rentile/kmp-linuxx64/maven-metadata.xml.md5`.~~ **Done.** The metadata
   document itself had landed and listed `0.11.1`; only its checksum was stale (published
   `338abcf7999537bd49aa84c31ccad0e9` against an actual `54800fb83b626c608df856bab9650119`), which a
   checksum-verifying or dynamic-version consumer can trip on. Publishing `0.11.2` rewrote that
   document and its checksums, and the published `md5` now matches. Do not repeat this step.
2. `./gradlew -PVERSION_NAME=0.11.1 :kmp:publishMacosArm64PublicationToR2Repository`. Still
   outstanding, and now optional: `0.11.2` is published whole, including `kmp-macosarm64`, so a
   consumer on a macOS target moves forward rather than waiting for `0.11.1` to be completed.

A clean `0.11.2` was the alternative, and it worked — the failing object was readable and writable,
not permanently broken — but it consumed a version rather than completing this one. That is what
happened: `0.11.2` published all eight coordinates and both public-verification steps ran. The
release workflow cannot do either repair itself: it rejects an existing primary POM by design, which
is what makes a released coordinate immutable.

**Do not consume `0.11.0` at all.** It has the identical `macosArm64` gap from the identical failure
one run earlier, and unlike `0.11.1` nothing was gained by it — it exists only because a released
coordinate cannot be rebuilt, so the repair at the time was the next number.

Render operations gained a priority. See
[ADR 0032](../adr/0032-rendering-has-a-priority-and-it-is-the-callers.md).

## What changed

Three signatures gained a trailing defaulted parameter:

```kotlin
render(batch, tiles = batch.tiles, priority = RenderPriority.NORMAL)
renderRaw(batch, tiles = batch.tiles, priority = RenderPriority.NORMAL)
render(style, tiles, options, resourceAccess, substitutionPolicy, priority = RenderPriority.NORMAL)
```

`RenderPriority.URGENT` marks a tile the caller is about to present, or one whose absence pauses
presentation. `NORMAL` marks read-ahead. A freed metatile worker goes to an `URGENT` request whenever
one is waiting, and to a `NORMAL` one only when none is; ordering within a level is unchanged FIFO,
and a tile already drawing is never pre-empted.

## What you have to do

**Recompile.** Adding a parameter changes the JVM and klib signatures, so a consumer built against
`0.10.x` does not link against `0.11.1` even though its source compiles unchanged. That is callers;
an *implementer* of `BasemapRasterizer` — a test double, most likely — also edits three overrides,
because an override must declare the parameter even when it ignores it.

**Discard nothing.** Priority is a scheduling decision and reaches nothing else: it does not enter an
output tile's request key or content key, and two tiles rendered at different priorities are
byte-identical. Cached raw resources, cached rendered output and renderer semantics all carry over.

**Nothing else changes by default.** Every existing call site keeps `NORMAL` and therefore keeps its
exact previous behaviour, which is one FIFO queue.

## What to do with it

Mark the tiles someone is waiting for, and only those. The mechanism is relative: a caller that
passes `URGENT` everywhere has one FIFO queue again and has gained nothing. It is worth exactly what
the caller's honesty about its own read-ahead is worth.
