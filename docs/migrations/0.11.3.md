# Migrating from 0.11.2 to 0.11.3

`0.11.3` is a performance release. It changes no public type, no signature, no key and no pixel, so
this is a version bump and nothing else. The source tree declares `VERSION_NAME=0.11.3`; that
declaration requests the release but does not prove it has been published. Upgrade only after
`com.rohittp.rentile:kmp:0.11.3` resolves from `https://maven.rohittp.com`.

A raster or DEM source tile is now decoded once for every draw of a prepared batch that reads it,
rather than once per draw. See
[ADR 0034](../adr/0034-share-a-decoded-source-tile-across-the-draws-that-read-it.md).

## What changed

Nothing you can call. `checkKotlinAbi` reports no change to the JVM or klib ABI, so `0.11.3` is a
drop-in replacement for `0.11.2`: no recompile is required, and an implementer of
`BasemapRasterizer` overrides nothing new.

What changed is inside `render` and `renderRaw`. `0.11.2` fixed this for the sprite atlas; this
fixes it for the source tiles themselves.

**Hillshade is where it matters.** A slope needs the DEM tile under the output tile *and its eight
neighbours*, and adjacent output tiles' neighbourhoods overlap almost entirely, so a metatile
decoded the same DEM many times over. Measured on macOS arm64 with Skiko 0.148.2 over 512 px DEM
tiles encoding to 381 KB, the size providers actually serve:

| Session | DEM tiles read | distinct | before | after |
|---|---:|---:|---:|---:|
| 2×2 metatile at the source's zoom | 36 | 16 | 111.3 ms | 24.5 ms |
| 4×4 metatile at the source's zoom | 144 | 36 | 435.3 ms | 43.1 ms |
| 4×4 metatile overzoomed ×4 | 144 | 9 | 434.7 ms | 14.4 ms |

Whole-session wall clock for the overzoomed case: **507.5 ms → 402.9 ms**. Hillshade's own
arithmetic is the larger half of that session and this release does not touch it.

**Raster changes only when you overzoom.** At a raster source's own zoom each output tile has a
source tile of its own, so there is nothing to share and this release does nothing at all — no
saving, and no decoded pixels retained. Above the source's maximum zoom one covering tile serves
`childScale²` output tiles, and that is where the repeat was:

| Session | draws | distinct source tiles | before | after |
|---|---:|---:|---:|---:|
| 4×4 metatile at the source's zoom | 16 | 16 | 34.5 ms | 34.0 ms |
| 4×4 metatile overzoomed ×4 | 16 | 1 | 47.0 ms | 34.0 ms |
| 52 tiles overzoomed ×2 | 52 | 16 | 153.6 ms | 88.0 ms |

## What you have to do

**Discard nothing.** Output request keys, content keys and renderer-semantics markers are all
unchanged, because the pixels are unchanged: the same decode of the same bytes, read the same way
into the same per-draw bitmap or surface. This was checked, not assumed — 108 tiles across six
styles at three output sizes through both `render` and `renderRaw`, on one worker and on four, all
324 PNG digests, raw RGBA digests and content keys identical before and after. Cached raw resources
and cached rendered output carry over.

**Nothing about the shape of your calls changes**, but the same two shapes that `0.11.2` made
cheaper get cheaper again:

- Rendering many tiles from **one prepared batch** decodes each source tile once, however many
  `render` or `renderRaw` calls you split those tiles across. Rendering a hillshade metatile as one
  batch is now markedly cheaper than rendering its tiles as separate batches.
- **Each prepared batch decodes its own.** Two batches of one style decode twice. Preparing one
  batch per tile stays the expensive shape.

**A batch holds decoded source pixels until you close it — but only where they are reused.** A
decode is retained only for a source tile more than one of the batch's draws reads, so a raster style
at its own zoom retains nothing and a 4×4 hillshade metatile retains roughly 32 MiB for its 512 px
DEM neighbourhood. That is below what four concurrent workers already held transiently, each with a
nine-tile neighbourhood of its own. Closing prepared batches promptly, as `instructions.md` already
shows, is what keeps it to one batch at a time.

**One consequence is visible if you re-render single tiles.** Re-rendering one tile of a batch
decodes again whatever that tile alone reads — for a tile at the corner of a hillshade metatile, the
one DEM no other tile of the batch needs. Before this release that re-render decoded the whole
nine-tile neighbourhood, so it is still strictly cheaper; it is simply not free.

## Release completeness

**`0.11.3` is whole.** All eight coordinates are published and signed — `kmp`, `kmp-android`,
`kmp-jvm`, `kmp-iosarm64`, `kmp-iossimulatorarm64`, `kmp-macosarm64`, `kmp-linuxx64` and
`kmp-linuxarm64` — each with a non-empty binary, a `.pom` naming `0.11.3`, a `.module` and a PGP
signature, and every coordinate's `maven-metadata.xml` carries `<release>0.11.3</release>` and
matches its own published `md5` and `sha1`. That last check includes
`kmp-linuxx64/maven-metadata.xml.md5`, the object whose write raised the R2 `500` that truncated
`0.11.0` and `0.11.1` and that `0.11.2` repaired: it is still consistent, so the repair held.
Checked from outside CI, against `https://maven.rohittp.com`, and confirmed by resolving
`com.rohittp.rentile:kmp:0.11.3` credential-free from a fresh Gradle user home and compiling against
`jvm`, `macosArm64`, `iosArm64`, `iosSimulatorArm64`, `linuxX64` and `linuxArm64`. The release
workflow also completed successfully, which corroborates that but is not what proves it.

`0.11.0` and `0.11.1` remain published without a `kmp-macosarm64` coordinate. A released coordinate
is immutable, so that does not change; `0.11.2` or later is the version to move to. See the
[0.11.1](0.11.1.md) and [0.11.2](0.11.2.md) ledgers.
