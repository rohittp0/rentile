# Lay out labels from glyph metrics

Rentile will lay out Labels from the signed-distance-field metrics carried by the Glyph Ranges its style names — advance, bearing and bitmap extent — and will not shape text through a platform font stack. Skiko already publishes `Font`, `Typeface`, `TextBlob`, `TextLine`, `shaper.Shaper` and the whole `paragraph` package in `commonMain`, so this is a deliberate choice not to use an available dependency rather than a limitation.

Shaping through Skia requires a `Typeface`, which means either font bytes the caller supplies or a platform font manager. A new required consumer input contradicts the injected-adapter boundary, and platform font managers differ by operating system, so the same style and tile would produce different glyph geometry on Android, Apple and headless Linux, where fonts may be absent entirely. Glyph Range metrics are integers fixed by the provider's own glyph encoding, so layout arithmetic is identical on every published target and needs no font file, no font manager, and no new adapter. The style's glyph endpoint is also the resource the style already points at for exactly this purpose.

The cost is that metric layout cannot perform bidirectional reordering or contextual joining. A Label whose evaluated text requires them is excluded with a diagnostic rather than laid out incorrectly, which follows the compatibility profile's existing practice of excluding what it cannot render faithfully and saying so, instead of emitting output that looks plausible and is wrong. Scripts that need many codepoints but no reordering, notably Chinese, Japanese and Korean, are unaffected and remain in scope; they make Glyph Range fan-out the quantity to bound, which is why acquisition carries an explicit per-batch range ceiling.
