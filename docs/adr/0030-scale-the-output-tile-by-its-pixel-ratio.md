# Scale the output tile by its pixel ratio

Rentile accepts `outputSizePx` of 256, 512, 1024 and 2048, and treats the value as a **device pixel ratio expressed as a size**: style evaluation happens at the output tile's own `z` whatever the size, and `outputSizePx / 512` scales every quantity the style measures in pixels. One output zoom therefore produces the same cartography at every supported size — the same features, the same label set, the same relative ink — with more pixels. A 2048 px tile is sharper than a 512 px tile of the same coordinate; it is emphatically not the `z + 2` tile whose pixel budget it happens to share. This is the size clause of [ADR 0013](0013-use-one-explicit-output-pixel-size.md) widened, and its scaling clause implemented.

The reason to widen it is a consumer's request fan-out. Style pixel values are resolution-independent to a vector renderer, so device density costs it nothing in tile count; Rentile rasterises, so density is paid in tiles. A consumer on a 3x-density screen renders its camera at `zoom + log2(3)` and, selecting basemap zoom by `log2(512 / tileSize)`, fetches two levels deeper than a vector renderer would for the same view — around nine times the tiles, measured at 930 against 104 for one route. At `tileSize = 2048` that shift becomes `-2`, one tile replaces sixteen, and the device pixels per unit of ground are unchanged, because `2048 / 512` is exactly `3 * 2^0.415`: the ratio the two extra zoom levels cost. The trade is deliberate and it is a good one — measured on a host JVM, one 2048 px tile costs 160 ms of draw and PNG encode against 27 ms for one 512 px tile, so covering the same ground costs 160 ms rather than sixteen times 27, and 93 KB of PNG rather than sixteen times 18.

Scaling is applied as a transform on the drawing canvas rather than as a multiplier threaded through each evaluated property, and that is the substance of the decision rather than an implementation note. The draw path works in a fixed 512-wide style space and never sees the output size at all, so geometry and ink cannot drift apart. Before this, they had: MVT coordinates were mapped through `outputSizePx` while `line-width`, `icon-size`, `symbol-spacing`, sprite pattern periods, halo widths, blur radii, collision boxes and the `symbol-avoid-edges` bound were all applied as raw output pixels. At 512 those agree by construction. At 256 they did not, so a `line-width` that evaluated to 14 painted 14 rows into a tile with half the ground resolution — half the pixels carrying full-weight ink. Extending that upward would have inverted at 2048 into quarter-weight ink over sixteen times the area. Two mismatched units also went unnoticed for the same reason: `symbol-spacing` in style pixels was compared against arc length in output pixels, so a line's icon repeat count changed with the output size, and a collision box's extent was in style pixels while its centre and edge bound were in output pixels. Both are consistent now because neither space exists any more.

`outputSizePx = 256` consequently renders differently than it did before this decision: its ink is half what it was, which is what "half the pixels" was always supposed to mean. That is a pixel change for identical style, tile, options and resources, so both output-key renderer-semantics markers advance — the request key to `rentile-output-request-3` and the content key to `rentile-output-4` — and a caller-owned cache cannot serve the old renderer's tiles. 512 is byte-identical: at the reference size the transform is the identity.

Two ceilings now cover the output surface as well as source imagery, because the surface Rentile allocates for itself had no bound at all while the largest one was 1 MiB and is 16 MiB at 2048: `maxRasterDimensionPx` against the size and `min(maxDecodedRasterBytes, maxResidentDecodedBytes)` against `outputSizePx² * 4`, both checked before Skia is asked for the surface, both reported as `SafetyLimitException`. Neither default needed raising — 8192 px and 256 MiB clear 2048 px and 16 MiB — so the check exists to make a host's own tightening diagnosable and to fail a future size that outgrows them, rather than to permit this one. A refused allocation is also wrapped now: Skia reports one as a bare `require` failure, which would have crossed the public API untyped.

Two things do not scale, and both are correct. The **label path** takes no `RenderOptions` and is untouched: its geometry is geographic, in degrees, or in em at `text-size / 24`, and its pixel-valued scalars are style pixels at ratio one. A consumer compositing labels over a tile above the reference size applies `outputSizePx / 512` to them itself, exactly as it already applies its device pixel ratio — and that independence is what keeps the label request and content keys free of an output size. **Raster imagery** cannot exceed its source: a provider's raster `tileSize` is capped at 512 by the Style Specification set Rentile accepts, so at 1024 and 2048 the exact-size match that [ADR 0009](0009-use-only-proven-raster-pass-through.md) requires can never hold, every raster layer takes the composite-and-re-encode path, and a raster basemap is bilinearly magnified rather than sharpened. Vector styles gain the full benefit; raster styles gain only the reduced request count.
