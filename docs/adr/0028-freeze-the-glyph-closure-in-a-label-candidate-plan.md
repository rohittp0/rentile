# Freeze the glyph closure in a label candidate plan

Rentile will report which Glyph Ranges a Label acquisition needs before acquiring them, through a Label Candidate Plan that both the report and the acquisition read, rather than through a stateless call that answers the question on its own. `planLabelCandidates` acquires the batch's Label Tiles, decodes and evaluates them, and freezes the Glyph Closure; `acquireLabelCandidates(plan)` fetches exactly that closure and assembles the batch. A consumer that must know a URL before it is fetched preregisters from the plan it then hands back.

The requirement comes from consumers that proxy Rentile's transport behind an exact-URL firewall. Every other resource class is derivable from the style document before acquisition begins, so such a consumer can preregister it; Glyph Ranges are not, because the `(fontStack, rangeStart)` set falls out of text inside decoded vector tiles that never cross the boundary. Without this the glyph fetch is refused, and no label can be drawn at all. The alternatives are worse than the API: pattern-matching one resource class carves an exception into the firewall's only invariant, and for the one class whose URLs are influenced by tile content; preregistering the bounded space costs 256 routes per font stack, per frame.

The obvious shape - a stateless `glyphClosureFor(style, tiles)` - is the one that does not work, and its failure is quiet. `acquireLabelCandidates` acquires its own Label Tiles, so a separate call would acquire them a second time, and under normal revalidation or reload the second acquisition can legitimately return different bytes. The reported closure would then under-approximate the acquisition that follows it, which presents as labels intermittently not drawing, with no error anywhere. Binding both to one frozen list makes that divergence impossible rather than unlikely, and costs a second decode of the viewport nothing, since the plan retains only evaluated labels and not the decoded tiles.

Two consequences are deliberate. The plan reports identities and composes URLs from a template the caller supplies, never emitting the style's own: the glyphs template is held as a protected URL because it can carry the provider credential, and it verifies the caller's copy against its own redacted form so a mismatched template fails loudly instead of preregistering routes that will never be fetched. And CONTEXT.md's standing position that a Label Candidate Batch cannot freeze its closure before acquisition was stated too strongly: a Glyph Closure cannot be frozen before Label Tile acquisition, but it can be frozen after it. The closure is two-stage rather than absent. A Label Candidate Batch is still not a Prepared Batch, and labels still cannot be folded into `prepareBatch`.
