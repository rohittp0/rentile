# Label placement belongs to the consumer

Rentile will prepare Labels and never draw them into an Output Tile. As of `0.6.0`, the Label closure is every visible text-bearing vector symbol layer rather than only place-name source layers. Rentile resolves which features produce text, the text after style evaluation, the font stack, size, anchor, offset and justification, the glyph geometry those strings need, and any paired icon. Point candidates carry an anchor; line and line-center candidates additionally carry their geographic source line, selected tangent, and requested repeat spacing. The consumer projects each Label Candidate into screen space, resolves collision and priority across its whole viewport, applies depth and occlusion, and draws.

Two independent reasons rule out the obvious alternative of rasterizing text into the tile like any other layer. An Output Tile is a mercator ground texture, so anything baked into it is baked into the ground: a consumer viewing that texture under a pitched perspective camera sees text compressed vertically toward the horizon, sheared by bearing, and reduced to sub-pixel height in the far field, whereas map text must stay upright and constant-size in screen space at every camera orientation. Separately, correct label collision is a screen-space problem across the entire viewport, while Rentile's existing symbol collision is tile-local and evaluated in tile space; two Labels in different tiles can overlap on screen without overlapping in any tile, and whether they do depends on the camera, so no tile-local decision is right for all cameras.

The consequences are deliberate. Rentile acquires and decodes Glyph Ranges but owns no text rasterization, no screen-space collision, no occlusion, and no fade behaviour. The Output Tile API remains separate, and consumers that never ask for Labels make no Glyph Range requests. A consumer that does ask can now receive more candidates and resources because road, point-of-interest, water, terrain, protected-area, and other label layers are no longer silently outside the closure. Because the Glyph Ranges a tile set needs depend on decoded feature properties rather than on style and tile identities alone, a Label Candidate Batch cannot freeze its closure before its Label Tiles are acquired, and is therefore not a Prepared Batch; labels are not foldable into `prepareBatch`. It can freeze that closure *after* them, which is what a Label Candidate Plan holds — see [ADR 0028](0028-freeze-the-glyph-closure-in-a-label-candidate-plan.md).

A paired icon belongs to the Label Candidate even when its dimensions depend on the text. Rentile carries the sprite geometry, paint, collision intent, map-or-viewport alignment, `icon-text-fit` inputs, and a semantic anchor on the final fitted box; pre-fit pixel anchor shifts are not part of the contract. The consumer has the glyph bounds needed to apply that fit and must collide the text and icon as one symbol. Sprite pixels and SDF/RGBA metadata remain consumer-owned and are resolved from `LabelIconRef.imageName`; Rentile does not publish a sprite atlas through the Label Candidate Batch. This label-facing rule is intentionally broader than the Output Tile repair rule in [ADR 0026](0026-repaired-layers-degrade-and-author-intended-layers-fail.md), where Rentile cannot rasterize text-dependent icon geometry. The public data-class changes and cache invalidation required by this expansion are recorded in the [0.6.0 migration guide](../migrations/0.6.0.md).
